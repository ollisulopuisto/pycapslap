## 2026-11-01 - Direct indexed lookup table for FontMetrics glyph advances
**Learning:** `FontMetrics::measure` is called pervasively across line breaking, caption justification, and ASS generation. Previously, every character lookup performed a `HashMap<char, f32>` query with hashing overhead (~870 ns per line measurement). Because bundled font advances are only populated for the Latin and Latin Extended-A range (`0x20..0x17F`), storing advances in a fixed-size direct lookup array `[f32; 0x180]` (1.5 KB per font) eliminates hashing overhead entirely for standard text, reducing per-line measurement latency to ~58 ns (a ~15x observed speedup). Characters outside this range transparently fall back to the HashMap or fallback advance.
**Action:** In Rust core text-processing or metric calculation loops where the domain is mostly ASCII / Latin, prefer direct array indexing `[f32; 0x180]` over `HashMap<char, _>` lookups.

## 2026-11-02 - Hoist cue_lines layout computation across word windows in previewLayout
**Learning:** In `captions::generate_preview_layout`, karaoke cues emit one preview cue per word window (e.g. 5-8 windows per segment). `cue_lines` computes the cue's multi-line layout and line-level font sizing (`steady_lines` / `justify_two_lines`). Because line breaks and line font sizing are constant across the entire segment regardless of which word is currently highlighted, re-evaluating `cue_lines` in every window loop caused N+1 redundant layout computations per segment. Hoisting `cue_lines` once per segment and passing `&cue_layout` into `preview_lines` cut `generate_preview_layout` internal latency from 3.02 ms to 1.34 ms (~2.25x observed speedup).
**Action:** In caption or preview layout generation where word-level highlights or sub-windows are generated for a segment, compute the segment's line layout once and reuse it across all window iterations.

## 2026-11-03 - Binary search for playback preview cue lookup
**Learning:** In `MainWindow._cue_for_position`, the preview layout cue is looked up on every video position tick (and during scrubbing/seeking). In karaoke mode, `_preview_cues` contains an entry per word window (often 500-2,000+ items for a typical video). A linear scan took ~42 µs per query at 1,000 cues (~415 ms for 10k ticks). Precomputing sorted start times `_preview_cue_starts` and using `bisect.bisect_right` cuts query latency to ~0.49 µs per query (an observed ~85x speedup for 1,000 cues and ~150x at 2,000 cues), keeping playback timer handler execution well under 1 µs on the GUI thread.
**Action:** When querying ordered timeline intervals on continuous playback/scrubbing signals, maintain a parallel `starts` array and use `bisect.bisect_right` instead of linear iteration.

## 2026-11-04 - Binary search for timeline segment selection on mouse press
**Learning:** In `VisualTimelineWidget.mousePressEvent`, finding the clicked segment previously scanned `self.segments` linearly, incurring ~24.8 µs per click query at 1,000 segments on the GUI thread. Because `self.segments` is chronologically ordered by `start_ms`, searching with `bisect.bisect_right(self.segments, target_ms, key=lambda s: s.start_ms) - 1` cuts lookup time to ~1.4 µs per query (an observed ~17.5x speedup at 1,000 segments), preventing input latency on mouse press / timeline scrubbing.
**Action:** For interactive timeline click/scrub handlers targeting chronologically sorted segment lists, use `bisect.bisect_right` with `key=lambda s: s.start_ms` instead of linear loops.

## 2026-11-05 - Binary search for caption panel segment row lookup
**Learning:** In `CaptionPanelWidget._row_for`, mapping a `CaptionSegment` to its table row index first attempts an `id()` lookup in `_row_of`. When segment instances originate from outside the exact in-memory panel list (such as across project reload/save, cloned models, or review imports), it fell back to an O(N) linear scan `next((i for i, seg in enumerate(self.segments) if seg == segment), -1)`. For 1,000 segments, this linear scan averaged ~95.2 ms across 500 lookups (~190 µs per query on the GUI thread). Because `self.segments` is chronologically ordered by `start_ms`, searching with `bisect.bisect_left(self.segments, segment.start_ms, key=lambda s: s.start_ms)` and checking matching timestamps drops average lookup time to ~1.08 ms (~88x observed speedup), eliminating GUI frame drops on playback cue updates.
**Action:** When locating objects by equality in chronologically ordered segment lists where identity lookup might miss, use `bisect.bisect_left` keyed on `start_ms` with timestamp-bounded verification instead of scanning the full list.

## 2026-11-06 - Binary search for active caption segment in review tool
**Learning:** In the client review web tool (`review/review.js`), `requestAnimationFrame(tick)` runs on every video frame (60 FPS during playback) and invokes `showCaption()` and `highlightActive()`, querying `activeIndex(segments, ms)`. Previously, `activeIndex` used `segments.findIndex(...)` performing an O(N) linear scan twice per frame (120 scans/sec). Simulating 10 minutes of playback (72,000 animation frames, 144,000 queries) against 1,000 segments took 240.97 ms of main-thread CPU time (~1.67 µs per query). Because caption segments are chronologically sorted and non-overlapping, replacing `findIndex` with an O(log N) iterative binary search cuts execution time across 72,000 frames to 10.61 ms (~0.074 µs per query, an observed ~23x speedup), preventing UI thread jank and frame drops during client review video playback.
**Action:** When querying active time intervals on continuous playback/animation tick handlers in JavaScript/TypeScript, use binary search instead of `findIndex` on sorted interval collections.
